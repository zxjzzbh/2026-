# 基于三组标注数据的红绿灯识别

使用用户已经标注的154张图像开发，原图和人工标签不改写。本版是红绿灯视觉识别、连续绿灯确认与任务逻辑接口；没有连接舵机、ESC或UART输出。

## 数据依据与真实限制

| 批次 | 数量 | 人工标签 |
|---|---:|---|
| 室内正对灯具1米 | 76 | 红25、黄23、绿23、全灭5 |
| 室内正对灯具0.5米 | 70 | 红26、黄18、绿24、全灭2 |
| 无灯背景 | 8 | 无灯8 |

三组均有两路图像，主USB2.0相机79张，第二路H65共75张，没有人工灯体框。所有场景都在室内；0.5米主摄图像有裁切，H65亮灯图像严重过曝。

这些图像都在开发中检查过，因此以下数字是**开发集回放结果，不是独立测试或室外比赛准确率**。模型不按文件名、哈希、人工标签或固定画面坐标猜颜色；运行时只看图像特征。检验按相机、整批次分别统计，不把相邻帧随机拆分来宣称独立准确率。

| 来源 | 回放正确数 | 绿灯召回 | 非绿误判为绿 |
|---|---:|---:|---:|
| 主USB2.0相机 | 76 / 79 | 24 / 24 | 0 |
| H65广角相机 | 8 / 75 | 0 / 23 | 0 |

主摄剩余3张为2张红灯和1张黄灯未可靠识别，输出未知／未检测到，保持等待。H65多数失败来自过曝后的颜色和灯圈证据丢失，所以**主摄作为红绿灯判断主源，H65只作辅助观察**。这不影响斑马线继续使用H65。8张背景都没有产生绿灯。

全体154张的严格状态回放为84张匹配；不能把主摄76/79写成整套双摄总体准确率。完整混淆统计、错误样本、逐图结果和哈希见 `run/traffic-model-20261009/evaluation-final/`。

## 技术栈与算法

- Python、OpenCV 4.11、NumPy 2.2.6，配置为JSON；不使用ROS或新YOLO权重。
- HSV颜色轮廓与灰度Canny边缘，拟合可见圆／椭圆灯罩。
- 用横向三灯相对位置、间距和尺寸建立候选灯组，不依赖人工框或固定ROI。
- 支持灯体部分接近画面边缘；缺失过多则保持未知。
- 对比三灯内部亮度、发光面积、白色过曝核心及分布在周围的对应色晕，避免仅凭灯罩颜色判断。
- 没有明显白色发光核心时，需要更强的亮度差，降低明亮灯罩反光被当作发光的可能；极端光照仍需新数据验证。
- 灭灯、多个可信候选、证据冲突或图像失效不会变成绿灯。
- 绿灯需至少3张不同的新帧，并持续至少0.6秒。红、黄、灭灯、未知、重复帧、乱序、换灯组或超过0.8秒的画面间隔会取消绿灯确认。

`traffic-signal.json`保存阈值和数据来源；`field_verified`仍为false。建议继续采室外顺光／逆光／阴影、不同摆位的独立新批次验证。H65若后续调整曝光，需要重新采集和评价，不能认为当前识别已解决它的严重过曝。

## 代码入口

| 文件 | 用途 |
|---|---|
| `src/carvision/traffic_signal.py` | `TrafficSignalDetector`定位和灯色、`SignalStability`时序确认、`TrafficLightStopLogic`红转绿任务接口 |
| `configs/traffic-signal.json` | 阈值、绿灯确认条件、推荐相机、开发批次 |
| `src/carvision/traffic_signal_evaluation.py` | 校验图像哈希并按相机／批次回放，保存报告与清单 |
| `src/carvision/traffic_preview.py` | 读取现有预览服务，只发GET；独立于文件采集器和车辆控制 |
| `tools/traffic_signal.py` | `evaluate`、`image`、`live`命令行入口 |

在电脑项目根目录回放三组标注：

```powershell
.\.venv\Scripts\python.exe vision/tools/traffic_signal.py evaluate --output run/traffic-replay-new
```

单张真实图片检查：

```powershell
.\.venv\Scripts\python.exe vision/tools/traffic_signal.py image --input 真实图片路径.jpg --output run/traffic-image-new
```

电脑观察车端主摄20秒：

```powershell
.\.venv\Scripts\python.exe vision/tools/traffic_signal.py live --preview http://100.124.156.117:8080 --camera primary --seconds 20 --output run/traffic-live-new
```

输出目录每次用新名字。`observations.jsonl`记录原始识别、连续确认、画面来源及只读任务意图，`summary.json`记录帧数／错误。没有取得图像会报失败；没有驱动车辆的参数。

树莓派相同入口使用项目 `.venv/bin/python` 和 `--preview http://127.0.0.1:8080`。本次已在Pi做只读4秒检查，得到31帧，全部判断全灭，图像算法每帧约23–33 ms；没有重启车控服务或发出运动指令。这是当前场景时延，不能当作所有光照的最大时延保证。

## 实时页面

电脑采集页 `http://127.0.0.1:8091/` 已接入新识别，显示原始灯色、绿灯确认状态和橙色自动灯组框。绿色框仍是人工标注框；新预测不会覆盖旧人工标签或写进原JPEG。原批次分页和标签功能保留。

当前HTTP输入仍是480×360预览JPEG。远端帧号只是状态提示，不与JPEG严格绑定；电脑预览只能作为视觉观察。正式车端控制应接入具有精确时间戳的本机摄像头帧与实际车速／停车区反馈。

## 后续接入车辆任务

`TrafficLightStopLogic.update(...)`需要实际停车区内标志、已验证停稳反馈和新鲜图像。进入停车区后还要观察到红灯，再确认实际转绿；初始就是绿灯、单纯等到3或10秒、画面丢失都不能放行。输出只有 `hold`／`may_continue` 意图，不发送PWM。

这两组拍照距离不能代替红绿灯停车区几何标定。当前没有红绿灯前轮停车位置和制动距离闭环，因此不能把此视觉接口直接接成“见绿就开”。先在实际灯具上验证识别与红转绿过程，再接入停车区定位及执行层。
